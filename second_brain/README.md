# PopCount Second Brain: Zero-Hallucination VSA Associative Engine

Самодостаточный модуль ассоциативной памяти и символического рассуждения на базе **Vector Symbolic Architecture (VSA)** и **Hamming PopCount**.

Разработан как быстрый «второй мозг» (Long-Term Memory / Factual Knowledge Base) для локальных LLM (Llama, Mistral, Qwen) и агентных систем на этой машине.

---

## 1. Назначение и Архитектурная Роль

Вместо попытки конкурировать с трансформерами в свободной генерации текста на естественном языке, модуль берет на себя то, в чем LLM слабы:
1. **100% Точность Фактов (Zero Hallucinations)**: Хранение и извлечение реляционных фактов (`Subject -> Relation -> Object`) с детерминированной проверкой конфликтов.
2. **Мгновенное Обновление Без Дообучения (Zero-Shot Retraining)**: Запись связей и фактов в 4 КБ страницы памяти происходит за суб-микросекунды через VSA XNOR-связывание (`XNOR / PopCount`), без обратного распространения ошибки и градиентного спуска.
3. **Обнаружение Логических Противоречий**: Быстрая проверка на конфликт (`brain_check_conflict`), позволяющая отсекать галлюцинации LLM до вывода пользователю.
4. **Сублинейный Поиск**: Роутинг через SimHash-центроиды и FFF-дерево по 4 КБ страницам памяти.

---

## 2. Оптимизации Под Наше Железо (i7-11800H Tiger Lake)

- **Аппаратный AVX-512 VPOPCNTDQ**:
  Векторизация XNOR и подсчета единиц через `_mm512_ternarylogic_epi64(0xCA / 0x99)` и `_mm512_popcnt_epi64` с горизонтальной редукцией `_mm512_reduce_add_epi64`. Обработка 512 бит за 1-2 процессорных такта.
- **Устранение Задержек Win32 VEH (5.2 мс -> 0.0 мкс)**:
  Исключен тяжелый перехватчик `AddVectoredExceptionHandler` + `VirtualProtect(PAGE_NOACCESS)`. Подсчет задействованных страниц переведен на прямой потокобезопасный битмап `touch_page(page_id)`.
- **Куча Вместо Переполнения Стека (Heap RAII)**:
  Большие структуры (`PureNeuralReasoningEngine`, `NativeSublinearLLM`, `MultiLayerExpertRelayEngine` суммарно >3 МБ) аллоцируются в динамической памяти через `std::make_unique`. Проект больше не требует опасного линковщика `/STACK:67108864`.
- **RAII Weight Bank Guard (`AutoMappedWeightBank`)**:
  Автоматическое закрытие дескрипторов Win32 `UnmapViewOfFile` / `CloseHandle` и удаление временных файлов `.bin` при завершении работы.

## 3. Публичный C-ABI API (`popcnt_brain.h`)

```c
#include "popcnt_brain.h"

// 1. Создание экземпляра мозга
PopCountBrain* brain = brain_create(262144, "build/brain.bin");

// 2. Мгновенная запись факта
brain_store_fact(brain, "node_alpha", "routes_to", "node_beta");

// 3. Проверка на логический конфликт
if (brain_check_conflict(brain, "node_alpha", "routes_to", "node_gamma")) {
    printf("[!] Обнаружено логическое противоречие!\n");
}

// 4. Запрос отношения
char result[256];
if (brain_query_relation(brain, "node_alpha", "routes_to", result, sizeof(result))) {
    printf("node_alpha routes_to -> %s\n", result);
}

// 5. Очистка и освобождение ресурсов
brain_destroy(brain);
```

## 6. Обучение на своём текстовом корпусе (`--train`)

Архитектура намеренно **не** применяет обратное распространение к HSSA-стеку: блюпринт заменяет обновления трансформерного типа `O(B*N*d^2)` (многосекундный backprop) на `O(1)` онлайн-вставку (VSA-факт < 2 мкс, TT16-адаптер < 25 мкс) — это и есть штатный способ «обучения» (см. BRIDGE.md -> DECISIONS).

Единственный градиентно обучаемый компонент проекта — этот движок (STE-тренажер `train_arbitrary_corpus_end_to_end`). CLI даёт ему вход из файла:

```cmd
build\popcnt_brain.exe --train C:\path\to\corpus.txt --epochs 6 --seed 1337
```

- Словарь строится **из самого корпуса** при первом появлении слова (`NativeTokenizer::add_word`) — вручную задавать токены не нужно, работает любой UTF-8 текст.
- Опции: `--epochs N` (по умолчанию 6), `--seed N`.
- Вывод — JSON с обязательными проектом твёрдыми числами: `bytes`, `vocab_size`, `sentences`, `tokens`, `epochs`, `initial_errors`, `final_errors_inloop`, `train_transitions`, `live_replay_errors`, `accuracy_percent`, `train_time_ms`, `throughput_tokens_per_sec`, `converged`.
- **Две метрики ошибок, и они не равны.** `final_errors_inloop` — счётчик самого тренера: он считает ошибки на «замороженных» рекуррентных состояниях, снятых **до** первого обновления весов. `live_replay_errors` — честная метрика: корпус прогоняется заново авторегрегрессивно уже обученной моделью. Вторая всегда выше первой; `accuracy_percent` считается именно от неё, знаменатель — `train_transitions`, а не `tokens` (в корпусе 8 250 слов, но 8 250 переходов после `<bos>`; деление на `tokens` занижало точность).
- Код возврата `0` только при полной сходимости (`final_errors == 0`), иначе `1` — незамеренный результат не выдаётся за успех.

## 7. Релятивная память: свой домен, свой граф, свой аллокатор

`PureNeuralReasoningEngine` — это «не-LLM мозг»: он хранит отношения между
сущностями в 4 КБ-страницах 1 ГБ-банка и отвечает на вопросы о цепочках
связей. Он **не** зашит под один домен:

```cpp
// bootstrap-корпус -- параметр конструктора (по умолчанию UNIFIED_REASONING_CORPUS)
PureNeuralReasoningEngine engine(bank, DOMAIN_SEED_CORPUS);
```

Что движок берёт из корпуса:

- **словарь ролевых сущностей.** Кластеры ролей выводятся из декларативных
  строк корпуса. Раньше в обучение уходили только первые 20 декларативных
  строк, то есть словарь был ограничен 20 строками; теперь берутся все
  декларативные строки, и словарь следует за корпусом.
- **якоря вопросов.** Каждая надзираемая строка (<|user|> ... <|think|>) даёт
  прототип-траекторию, к которой маршрутизируется вопрос.
- **граф.** Цепочка, записанная в think-секции как `A -> B -> C -> D`, превращается
  в рёбра `A->B`, `B->C`, `C->D`. Строка, где в одной части стоят две сущности,
  — это список ролей, а не цепочка, и она отвергается.

Готовый пример домена — `second_brain/domain_seed_corpus.h` (складской конвейер:
32 узла, 3 хоста, 3 шифра, 2 семейства, 2 контура).

**Размещение страниц.** Релятивные регионы адресуются не по модулю
`BASE + (id & 1023)`, а через аллокатор, состояние которого лежит внутри банка
(открытая адресация, директория `owner -> страница`). Владелец (id сущности)
владеет одной или несколькими страницами; когда они заполнены, он получает
**ещё одну страницу**, а не теряет правило.

Сами регионы и метаданные аллокатора лежат **за пределами массива страниц
модели**: микро-эксперты модели маршрутизируются по всему массиву
(`expert_id = (u << 9) | v`), то есть обучение может записать любую его
страницу. Измерено: после 24 144 имитированных записей модели по массиву
**64 из 64 сохранённых правил выжили** (до переноса — 58 из 64). Файл банка
стал больше гигабайта, но остаётся разрежённым: диск занимают только
записанные блоки.

| | было | стало |
|---|---|---|
| 40 правил одного владельца | 16 выжили, 24 уничтожены молча | 40 выжили, 0 потерь |
| правил на регион | 16 384 | 20 000 (граф) / 58 000 (факты) страниц |

Замер — на уровне аллокатора, с произвольными ключами правил. Сам движок
кладёт в факты ключ «(субъект, отношение)», а объект живёт в значении, так
что на одного владельца приходится не больше `REL_COUNT` = 10 различных
ключей; измерить переполнение страницы на 40 правилах можно именно через
аллокатор.

**Честный отказ.** Если сущность из вопроса не удалось связать, движок не смог
определить роль вопроса или ответ не упоминает предмет вопроса, ответ содержит
маркер `[abstain]` вместо уверенного (и неверного) текста. Измерено на
31 вопросе: 15 узнаваемых форм, 6 парафраз, 10 никогда не встречавшихся --
неизвестные формы отказывают в 12 из 12, парафразы отвечают верно в 5 из 6.

**Токенизация.** Движок отделяет пунктуацию от слова (контракт ролевой
подпространности: `encode_prompt_role_subspace_bits` пропускает одиночные
`? ! . : ,` как отдельные токены). Тренер сырого текста оставляет пунктуацию
приклеенной: разделение стоит ему 0.49 п.п. на фиксированной референсной
точке (90.836% -> 90.342%, вне полосы 90.59-90.91). Оба числа воспроизводимы.

## 8. Обучение под задачу: два разных механизма

В движке две независимые вещи, которые можно обучить под свою задачу. Они не
взаимозаменяемы.

### 8.1 Политика (веса реально обучаются): STE-релей

`train_chained_expert_relay_ste` обучает тернарные веса в 4 КБ-страницах
экспертов на парах (состояние 512 бит -> токен-действие). Это и есть
«моментальный выбор»: состояние -> один из кандидатов, без генерации.

Что нужно от прикладной задачи:

1. **энкодер состояния** в 512 бит (тернарный кодек или эмбеддинг модели);
2. **учитель** — метки или награда: тренер работает в режиме teacher forcing,
   то есть он дистиллирует заданную политику, а не ищет её;
3. **короткий список кандидатов**: argmax по всему словарю (4096 слов) стоит
   20.3 мкс, по списку из 16 кандидатов -- 1.4 мкс (в 15 раз дешевле).

Измерено на этом хосте (i7-11800H):

| задача | обучение | точность | решение |
|---|---|---|---|
| 16-классовый выбор (свой энкодер, свой учитель) | 26 мс | 16/16 | **1.4 мкс** |
| штатный пример «змейка» | 200 мс, 63 страницы | 139/144 (96.5%) | **2.0 мкс** |

Механизм не привязан к змейке: змейка -- это только энкодер (9 целей x 16
масок опасности) и учитель (правило, написанное руками). Тест с
16-классовым выбором использует другой энкодер и другого учителя и учится
точно.

### 8.2 Память (веса не обучаются): релятивный мозг

Здесь «обучение» = дать корпус (параметр конструктора) и записать факты; граф
выводится из текста корпуса. Если ответ нужно выбрать **из памяти**, генерацию
можно не звать вовсе: разбор вопроса плюс обход графа в страницах.

| путь | что делает | измерено |
|---|---|---|
| прямой обход графа | ищет терминал цепочки | **24-29 мкс** |
| тот же вопрос через генерацию | строит текст ответа | **2033-2357 мкс** |

Разница -- **~84 раза**. Прямой обход отдаёт идентификатор узла (или строку),
а не связный текст: если ответ должен быть прозой, слой генерации нужен.

Оба пути закрыты регрессионным тестом `tests/test_popcnt_selector.cpp`
(сборка и запуск: `tests/build_popcnt_selector_tests.bat`).

### 8.3 Обучение без учителя: награда от среды

Тренер из 8.1 работает в режиме teacher forcing: он переносит заданную
политику в веса. Отдельный путь (`train_in_snake_gym_by_reward` +
`train_from_reward_ste`) обучает веса **по награде среды**, без ручного
правила: агент исследует (ε-жадный поиск с геометрическим затуханием ε),
среда платит за яблоко (+1), за смерть (-1) и за пережитый шаг (+0.01), а
сеть клонирует действия, которые окупились, и отталкивает те, что не
окупились. Отталкивание -- это тот же STE со сменой знака цели
(target = -эмбеддинг действия), поэтому score наказанного действия падает.

Метрика -- только слова среды (сколько яблок съедено, сколько шагов
прожито); сравнения с ручным правилом в оценке нет.

| политика | яблок/эпизод | шагов/эпизод |
|---|---|---|
| случайная | 0.00-0.05 | 3-4 |
| **обученная по награде, 3 000 эпизодов** | **10.5** | **75** |
| обученная по «голой» награде, 10 000 эпизодов | 6.7 | 94 |
| ручное правило (учитель) | 32.1 | 340 |

**Честно о «без учителя».** Ручных меток действий нет ни одной:
`compute_reward_optimal_action_for_training` в этом пути не вызывается ни
разу. Но прогресс-сигнал среды (расстояние до цели) -- это плотный
направленный сигнал, которого агент не наблюдает, поэтому чистая форма
(только яблоко, смерть и пережитый шаг) тоже реализована и измерена: она
учится, но медленнее (6.7 яблока за 10 000 эпизодов против 10.5 за 3 000 с
прогресс-сигналом). Что требуется от прикладной задачи: среда, которая
выдаёт награду, и наблюдение, которое кодируется в 512 бит.

Ограничение, которое видно по замерам: агент выигрывает у случайной
политики на порядки, но до ручного правила не дотягивает (10.5 против 32.1
яблока) -- обратная связь среды шумная, а состояние агента (направление на
цель и маска опасности) не описывает доску полностью, поэтому одна и та же
оценка состояния соответствует разным исходам.

### 8.4 Обобщение и «больше данных = хуже»

Две проблемы корпусного пути разобраны замером, и починил их один механизм.

**Что показало исследование (до правок).**

- **Обобщение.** На сплите по исходным файлам: 74.5% на виденном против 13.1%
  на невиденном. На подсловном сплите движок даёт **28.3876%**, а каузальная
  счётная модель (trigram -> bigram -> unigram, топ-1), обученная на тех же
  данных, -- **35.502%** (разрыв 7.1 п.п.): обобщаются счётные статистики, а
  не рекуррентная выборка. Правка при сверке: ранее цитированная модель
  "46.899%" своим skip-уровнем отвечала на вопрос "какой токен стоит МЕЖДУ
  предыдущим и СЛЕДУЮЩИМ" -- то есть прямо использовала заведомо известный
  правильный ответ (+12.7 п.п. из её 46.9); такой уровень не работает в
  живом драфтере, и число теперь цитируется каузально. На словном уровне та
  же поправка: цитировали 30.022%, каузальный chain с униграмм-фолбеком --
  38.462%. Oracle-роутинг стоит +5.05 п.п. Три варианта ключа (рекуррентный
  28.388%, split-subspace 28.758%, exact-bigram 25.504%) умещаются в полосу
  в 3 п.п.: **выбором ключа разрыв не закрывается, закрывают счётки**.
- **Потери от объёма.** Точность коррелирует с загрузкой страниц сильнее, чем с
  размером корпуса (r = -0.83 против -0.77). Механизм -- со-размещение: на
  странице 16 слотов, запись STE перезаписывает их молча. От 2k до 32k строк
  средняя загрузка растёт 1.94 -> 6.81, худшая страница держит 5 585 ассоциаций,
  5 259 страниц переполнены.
- **Просадка скорости.** Роутер сканирует фиксированные 512 суб-ключей -- он ни
  при чём. Выходной argmax стримит всю таблицу словаря (4.7 МБ на 72 763 слова,
  ~27 ГБ/с): 116.7 мкс на вызов при 46k слов против 0.36 мкс при 32 кандидатах.
  А словарь растёт вместе с корпусом.

**Что сделано.** Счётный backoff по идентичностям токенов (trigram -> bigram
-> skip -> unigram -- все уровни смотрят только назад) даёт множество
кандидатов вместе с частотой каждого кандидата, а решающее правило --
смесь: `тернарный dot + count_weight * bucket(count)`, где
`bucket(count) = floor(log2(count)) + 1` -- ПОРЯДОК ВЕЛИЧИНЫ частоты, а **не**
`log2(count)`. Шаг ведра весит весь вес (1024 очка при весе 1024), а модуль
dot'а, который выдаёт сеть, доходит до **7680** -- это замерено, а не
предположено (512 измерений, активации зажаты в +-15, веса тернарные +-1;
гейт печатает наибольший |dot| и следит за этим пределом). Прежняя заметка
"dot в пределах -512..+512" была НЕВЕРНОЙ. Поэтому счётный член -- сильное
ПРЕДПОЧТЕНИЕ, а не лексикографическое правило: при большой разнице dot'ов сеть перебивает ведро
(и свип это доказывает: рука 1024 и рука 4096 дают разные числа). 1024 --
измеренная точка БАЛАНСА между счётной статистикой и сигналом сети, а не
порог. Правило решения ОДНО и для тренировки, и для инференса
(`decide_token` -> `backoff_score`): иначе тренер оптимизирует не ту функцию, которая потом
действует, а скорость обучения не меняется вовсе (замер: 372.4 с против
370.7 с на 32k, пока шортлист стоял только в инференсе). Замер веса на
held-out сплите: 64 -> 34.51%, 256 -> 35.65%, 1024 -> **36.54%**,
4096 -> 35.73%. Потолок покрытия и размер шортлиста измерены на СОБСТВЕННЫХ
таблицах движка (175 876 held-out позиций): правильный следующий токен лежит

**Честно: границы механизма (измерены, не починены).**
- **Потолок покрытия.** На реальном сплите набор кандидатов k=32 содержит
  правильный преемник для **58.9%** невиденных контекстов (k=4 -> 48.2%,
  k=64 -> 60.4%, k=256 -> 62.1%, без ограничения -> 62.5%): около 41% невиденных
  контекстов физически вне досягаемости при k=32.
- **Фолбэк «пустой набор -> весь словарь» недостижим:** униграмм-таблица не
  пуста, поэтому для невиденного контекста доступны только 32 самых частотных
  преемника, а не весь словарь.
- **Возможен уверенно неверный ответ:** биграмм-фолбэк предлагает тех
  преемников, которые видел, а слово, встретившееся в другой роли, делает их
  неверными (backoff обобщается по СЛОВАМ, а не по ролям).
- **Невыигрышные переходы:** ограниченное решение не может выдать цель, которой
  нет в кандидатах -- 9.93% переходов на 32k и 12.49% на полном корпусе. Тренер
  считает их отдельно (`unreachable_targets`) и отдельно отдаёт покрытие
  таблицы (`shortlist_coverage_percent`), потому что отчётная точность -- это
  произведение качества сети и покрытия.
- **Базовый уровень поправлен (см. выше):** каузальная счётная цепочка на
  подсловном сплите -- 35.50% (не 46.9%); смесь движка **36.538%** выше неё
  на 1.04 п.п. Словная каузальная цепочка (38.46%) пока ВЫШЕ словного движка
  (25.51%) -- рычаг измерен только на подсловной задаче.
- **Со-размещение никуда не делось:** страницы по-прежнему держат 16 слотов, и
  записи по-прежнему их перезаписывают. Второй рычаг (сколько страниц одна
  трансформация затрагивает, `HSSA_CORPUS_TOP_K`) измерен отдельно: +0.6..+1.4
  п.п. точности ценой 15-28% пропускной способности и 18-38% времени
  тренировки, поэтому штатное значение осталось 4.
- **RAM:** на полном корпусе (1.79M строк) таблицы счётов -- около 558 МБ в
  памяти и пик 2.7 ГБ (промежуточная вложенная карта в 5 раз больше
  итоговой), сверх ~1.9 ГБ самой модели на таком словаре.
